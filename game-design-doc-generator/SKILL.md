# Game Design Document Generator

将用户的一句话或一段粗略游戏创意，扩展为完整、自洽、有说服力的游戏设计文档。本文档只处理玩法、规则、风格、场景、角色、操作、反馈和结构，不编写代码、不设计技术架构、不填写调参数值。

## 总体原则

- 忠于用户原始创意，不更换核心玩法、题材或场景。
- 补充类型必备规则，但不要凭空增加新的核心机制。
- 信息不足且有多种合理方案时，选择最贴合类型和原始创意的一种，并写明“设计决策：……，因为……”。不要反问，不留 TODO。
- 所有描述落到玩家做了什么、看到了什么、听到了什么和系统如何回应，避免“流畅”“炫酷”“精美”“难度适中”等空泛形容词。
- 可以写规则性数字，例如三条命、五张手牌、三选一；不要写调参数值，例如移动速度、伤害、冷却毫秒、震屏像素或颜色色值。
- 不直接照搬任何具体作品的标志性设计，只提炼设计意图并转化为适合本作的表达。

## Design Pillar

在设计文档开头先写：

```text
这个游戏最爽的那一秒是：________________。
```

后续每项设计都要能说明它如何服务这一秒。无法服务核心体验的内容应删除或标记为不适用。

## 输出结构

按以下顺序输出，具体模块必须根据项目类型取舍：

1. 一句话核心体验（Design Pillar）
2. 类型识别与标杆拆解
3. 设计轴判定
4. 核心玩法
5. 完整规则
6. 游戏风格与场景
7. 角色设定（存在角色时）
8. 操作与交互
9. 反馈表现
10. 结构性模块
11. 自检清单

不适用或会破坏核心体验的模块必须保留标题，并写明“不适用”或“禁止引入”的具体原因，不得静默省略。

## 一、类型识别与标杆拆解

先写清楚：

```text
这是一款【主类型】游戏，带有【次类型】成分，核心体验由【哪一个】决定。
```

列出 3 至 5 款代表作品，每款只说明它解决了该类型中的什么设计问题，不只罗列名称。

然后将类型要素分为三档：

| 档位 | 处理方式 |
|---|---|
| 必备 | 缺少就不像该类型或无法成立，一律补齐 |
| 常见 | 只补充服务 Design Pillar 的内容，其余说明放弃理由 |
| 特色 | 禁止照搬具体作品，只提炼设计意图并改写 |

逐条对照当前创意，并标注：已有、缺失需补、不适用、禁止引入。

## 二、设计轴判定

判断以下四条轴：

| 设计轴 | 可选取值 |
|---|---|
| 时间压力 | 实时 / 半实时 / 无时限 |
| 主要技能 | 操作精度 / 决策推演 / 资源规划 / 知识记忆 / 叙事共情 |
| 失败结构 | 即死重开 / 资源损耗 / 卡关不死 / 无失败 |
| 进度结构 | 无尽刷分 / 线性关卡 / 局内构筑 / 长线养成 / 分支叙事 |

根据判定写出模块取舍和反面禁区：

- 无时限或主要技能为决策推演时，不引入会摧毁推演空间的连击、倒计时等时间压力。
- 无失败结构时，不为了制造挑战强行添加失败条件。
- 不是无尽刷分时，不硬造分数系统。
- 无时限时，用关卡编排代替难度曲线。
- 主要技能为操作精度时，必须设计操作宽容度；其他情况说明为何不适用。

## 三、核心玩法

必须包含：

### 3.1 一句话玩法

使用“动词 + 对象 + 目标”的句式。

### 3.2 玩家动词表

列出玩家可以做的全部关键动作。每个动作说明：做了会怎样、什么时候使用、与哪个动作配合或冲突。动词太少或太多时说明取舍。

### 3.3 核心循环

写出玩家反复执行的动作序列，例如观察 → 判断 → 执行 → 看到结果 → 调整，并说明单次循环是几秒、几分钟还是一整局，以及循环之间如何连接。

### 3.4 核心张力

明确玩家每一刻在权衡什么，例如贪心多拿一个还是安全撤退、现在使用还是留到后面、走快路还是走稳路。写不出核心张力时，回到玩家动词重新设计。

### 3.5 变化来源

列出新对手、新地形、新道具、新规则和规则反转的登场顺序，并说明每项新内容改变了玩家原有的哪个习惯。

### 3.6 技巧上限

至少写出两个高手比新手多做到的具体操作或思路，说明它们为何足以支撑重复游玩。

## 四、完整规则

必须写清：

- 获胜条件、判定时机和判定优先级
- 所有失败条件；如果无失败，说明张力由什么承担
- 失败可归因：玩家失败后能用一句话说出因为什么输
- 实时游戏必须有可察觉的失败预警，禁止毫无征兆的秒杀
- 非实时游戏必须能回溯到具体错误决策
- 越界处理、条件冲突优先级和平局规则

## 五、游戏风格与场景

### 5.1 基调

用一句话定性，并说明基调如何强化 Design Pillar。

### 5.2 视觉风格

写风格类别和 2 至 3 个参考锚点；说明线条、形状语言、画面构图、视角以及它们为何服务玩法。

### 5.3 色彩职能

不写色值，只写主角、威胁、奖励和背景的颜色职能。可交互物必须比背景更易识别，且不能只靠颜色区分敌我或危险，必须叠加形状或图案。

### 5.4 场景与世界

说明故事发生地点、远景/玩法层/前景的作用，以及场景是否参与玩法，例如可破坏、可利用或会变化。

### 5.5 声音气质

说明音乐情绪和音效质感。不同关键事件必须能通过声音区分。

### 5.6 UI 与文案口吻

说明 UI 风格、提示、结算和按钮的说话方式，保持口吻统一。

## 六、角色设定

存在角色时，写主角外形、辨识点和待机/行动/受击/结束状态差异。

每种对手都写：

- 一句话威胁方式
- 一句话破解方式

不同敌人的威胁方式必须真正不同，不能只是换皮。叙事较重时，再补充角色动机、缺陷和说话方式。

## 七、操作与交互

- 写完整操作表，区分按下、长按和松开。
- 暂停、重开和静音必须可达。
- 操作精度型游戏必须写操作宽容度：游戏在哪些地方对玩家手下留情，以及要制造什么“是我反应快”的错觉。
- 教学采用“关卡即教学”，设计零风险场景让玩家自己发现操作，不写说明书式教程。

## 八、反馈表现

每次玩家输入和每次状态变化至少有两个感官通道回应。

逐项描述操作成功、操作无效、获得奖励、受伤受挫和局面结束时的视觉、声音和画面反馈。实时游戏必须有命中顿挫和画面冲击；非实时游戏必须有明确的决策确认。闪烁和震动必须可关闭。

## 九、结构性模块

按设计轴取用，并对不适用模块说明原因：

- 难度推进：仅适用于实时游戏；写增长维度、新能力、紧张与喘息和安全开局。
- 关卡编排：适用于无时限或线性关卡；按教学 → 变奏 → 组合 → 颠覆组织，并写每关考察内容、玩家应想通的关键句和三级提示。
- 有意义的选择：至少一个没有唯一正解的决策点，每个选项都有代价；验证不存在全局最优选项。
- 成长与胜任感：先声明成长是玩家技巧、玩家认知、角色能力或剧情推进，再说明玩家如何看见成长。
- 记录与进度：刷分游戏写计分维度和结算呈现；存档游戏写存什么、读档回到哪里和如何帮助玩家重新进入状态。
- 节奏：写单局或单章目标时长、失败后多久能重新操作，以及玩家在第 1 分钟、第 10 分钟和第 1 小时做什么。

## 自检清单

输出末尾必须逐项检查：

- [ ] 每条补充都来自用户原文或类型必备要素，没有凭空发明核心机制
- [ ] 没有直接照搬具体作品的标志性设计
- [ ] 没有空泛形容词或调参数值
- [ ] 核心张力清楚说明玩家每刻在权衡什么
- [ ] 每个变化来源都改变了玩家原有习惯
- [ ] 风格基调与核心玩法指向同一种感受
- [ ] 每种失败都能被玩家归因
- [ ] 不适用和禁止模块都说明了原因
- [ ] 操作、反馈、节奏和成长都能落到具体行为或画面

## 输出限制

默认只输出完整游戏设计文档和必要的设计决策说明，不输出代码、技术架构、实现步骤或调参表。除非用户明确要求，否则不要把这份设计文档改写成开发任务清单。
